# Assignment 3 - Parallel Matrix Multiplication

Big Data, ULPGC, academic year 2026-2027.

This project compares one equivalent sequential i-k-j matrix multiplication implementation with a parallel version using 1, 2, 4 and 8 Java worker threads. It uses the loop-reordered algorithm previously evaluated in Assignment 2. This repository contains actual results recorded on the student's Windows 11 laptop on 13 November 2026.

## Files

- `Assignment3Matrix.java`: Java 21 source (unchanged from the submitted project ZIP)
- `results_assignment3/raw_times.csv`: 125 individual time measurements (5 sizes x 5 methods x 5 repetitions)
- `results_assignment3/raw_memory.csv`: 125 separate JVM heap-delta observations
- `results_assignment3/summary.csv`: median time, IQR, memory estimates, speedup, efficiency
- `results_assignment3/correctness_tests.txt`: reported validation results
- `results_assignment3/Experiment_Setup.txt`: experiment settings and hardware details
- `plot_results.py`: produces figures from the CSV files

## Java compile/run

Use Java JDK 21. On Windows PowerShell, from the repository directory:

```powershell
javac Assignment3Matrix.java
java Assignment3Matrix
```

The program writes or overwrites the `results_assignment3/` directory relative to the current working directory. To reproduce the historical results, keep the supplied CSV files unchanged and run new experiments in a separate folder.

For a quick functionality test on smaller data:

```powershell
java Assignment3Matrix --quick
```

That produces `results_assignment3_quick/` and must not be substituted for the full benchmark.

## How the experiment works

Inputs are two `n x n` `long[][]` matrices generated by `java.util.Random` with seed `20261113 + n` and values 0..9. The same matrices are used in all 5 methods for each n. The parallel implementation partitions output rows into disjoint ranges, using the exact same i-k-j arithmetic loop as the sequential method. Each result is compared element-by-element against the sequential reference.

Time is measured with `System.nanoTime()` for a complete multiplication call; output allocation and, for the parallel methods, task submission and waiting are included. Input creation and thread-pool construction are excluded. Thread pools were prestarted. Five timed repetitions and two warmups were used per size and method. Tested sizes: 128, 256, 512, 768, 1024. Thread counts: 1, 2, 4, 8. Sequential uses the calling thread (reported as 0 worker threads).

Memory is _not peak RSS_: `raw_memory.csv` records a separate, approximate retained JVM heap delta after calling `System.gc()` (five observations). `estimated_three_matrices_mib` only counts numeric payload for A, B and C, excluding array headers, worker threads/stacks, pools and JVM overhead. These are different measurements.

Hardware: Windows 11, Intel Core i5-10210U, 4 physical cores, 8 logical processors, 7.72 GiB RAM (hardware record from Assignment 1 on the same laptop). The program reported Java 21 and 8 logical processors. Windows default affinity; none configured. No numerical-library worker threads. The JVM may run internal JIT/GC threads. Although at most 8 calculation workers were assigned per invocation, pools with 1+2+4+8 threads existed concurrently and were idle while other settings ran; this should be considered when interpreting total thread activity.

Limits: a 256 MiB numeric-payload budget and a post-run 30-second per-multiplication threshold are checked in code. No configuration exceeded either threshold. Times are not actively interrupted at 30 seconds.

Some measured speedups exceed the number of workers (notably n=512), with high IQR and inconsistent 1-worker performance. These should not be interpreted as evidence that parallelism exceeds ideal linear scaling. Differences between independently measured sequential and parallel medians can reflect JVM compilation, caching and benchmark noise.

The optional SIMD/vectorisation extension was not attempted.
